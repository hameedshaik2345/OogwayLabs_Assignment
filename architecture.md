# Architecture Document

## 1. Component Boundaries
- **Frontend (Next.js):** Handles the Chat UI and Artifact Viewer. Deployed on port 3000.
- **Backend (FastAPI):** Exposes `/api/chat` and `/api/sessions`. Handles RAG routing and LLM execution. Deployed on port 8000.
- **Database (PostgreSQL / SQLite):** Persists session history and user messages.

## 2. API Endpoints
- `GET /` - Health check.
- `POST /api/chat` - Receives user message, updates session in DB, routes to Agent, and returns AI response.
- `GET /api/sessions/{session_id}` - Fetches historical chat context for a given session.

## 3. Database Schema
**Table: `sessions`**
- `id` (UUID, Primary Key)
- `created_at` (DateTime)

**Table: `messages`**
- `id` (UUID, Primary Key)
- `session_id` (UUID, Foreign Key)
- `role` (String: "user" | "assistant")
- `content` (Text)
- `created_at` (DateTime)

## 4. Ingestion / Retrieval Flow
1. Transcripts are loaded from the `data/transcripts` folder.
2. The agent reads the context and attaches relevant transcripts to the system prompt (simulating RAG for the demo without needing a heavy Vector DB to install).
3. The response is grounded on these text files.

## 5. Security & Artifact Isolation
Generated artifacts (HTML/CSS/Markdown) are insecure by nature. The frontend `ArtifactViewer` mitigates risks by:
- Using `DOMPurify` to sanitize raw HTML before insertion.
- Rendering the sanitized HTML inside an `iframe` with `sandbox="allow-same-origin"`. This prevents scripts, popups, and top-level navigation, ensuring malicious JS generated by the LLM cannot execute in the main application context.
